# 可解释每日精选匹配设计

## 目标

在不复用 AGPL 项目代码的前提下，为“遇见路得”实现独立的、可解释的异性婚恋匹配系统。系统每天向进入匹配池的用户固定推荐至多 3 位候选，而非提供无限候选列表。

## 已确认决策

- 平台只支持异性婚姻匹配；性别为进入匹配池的必填资料。
- 每位用户每天最多获得 3 位精选候选；候选不足时不补足。
- 新增约 30 题的核心匹配问卷，覆盖信仰实践、婚姻观、家庭边界、子女、财务、生活方式六个维度。
- 用户最多将 5 项回答标记为不可妥协项；任一方的不可妥协项冲突即不互相推荐。
- 排序使用本地、确定性的规则引擎；AI 不参与候选排序、底线判断或分数计算。
- 前台展示匹配等级、3 条契合理由和 1 条沟通提醒，不展示精确百分比。
- 推荐阶段分级披露：匿名头像、年龄段、城市、信仰背景与匹配解释；双方心动后复用现有聊天和关系流程。
- 现有的入池资格、心动/跳过、双向心动、私聊和关系确认链路继续保留。

## 范围

第一期只实现问卷驱动的每日推荐，不包含：AI 文本评价、向量检索、照片展示、牧者人工撮合、推送通知、后台自定义题目编辑器或历史推荐分析报表。

## 数据模型

### 基础候选资料

`profiles` 新增：

- `gender`：`male` 或 `female`。迁移阶段允许旧资料为空，但进入匹配池前必须填写；用户仅可在尚未进入匹配池且不存在有效关系时修改。
- `preferred_min_age`、`preferred_max_age`：可为空；为空时不限制。双方年龄范围必须互相满足。
- `preferred_city_mode`：`any` 或 `same_city`；默认 `any`。双方任一方要求同城时，城市必须一致。

性别、年龄和城市是互相可见前就执行的基础过滤条件，不写入匹配理由。

### 问卷定义与答案

使用数据库中固定种子题库，而不是运行时由模型生成：

- `matching_question_versions`：题库版本及启用状态。
- `matching_questions`：题目、维度、排序、答案类型和是否可标为底线。
- `matching_options`：选项文案、规范化值与用于解释的短标签。
- `matching_responses`：用户当前题库版本的答案与是否标为不可妥协。

首版 30 题均为单选。每题有 3–5 个规范化选项；最多 5 题可设为不可妥协。更换题库版本时保留历史回答，但仅当前版本参与推荐。

### 每日推荐快照

- `daily_match_batches`：用户、日期、问卷版本、生成时间。
- `daily_match_recommendations`：批次、候选用户、原始分数、匹配等级、3 条理由、1 条提醒、状态。

`(user_id, recommendation_date)` 与 `(batch_id, candidate_id)` 必须唯一。首次读取当天推荐时生成快照；后续读取完全复用该快照。用户当天改问卷不会改变当日结果，次日重新计算。

## 候选筛选与评分

### 筛选顺序

1. 复用现有 `isInMatchPool`：资料、信仰档案、信仰测试、背书和配置要求的课程均合格。
2. 排除本人、已封禁账户、已有未结束关系、当天已跳过或已表达心动的关系。
3. 仅保留异性，且双方年龄范围、城市限制都满足的用户。
4. 双向检查不可妥协项；答案不兼容即排除。

### 加权分数

六个维度的基础权重如下，总计 100：

| 维度 | 权重 | 说明 |
| --- | ---: | --- |
| 信仰实践 | 30 | 教会生活、属灵成长、婚姻中的信仰实践 |
| 婚姻观 | 25 | 婚姻目标、沟通、冲突修复、角色期待 |
| 家庭边界 | 15 | 原生家庭、父母边界、居住安排 |
| 子女 | 12 | 是否愿意要孩子、养育理念与时间预期 |
| 财务 | 10 | 消费、储蓄、共同决策与负债态度 |
| 生活方式 | 8 | 城市流动、作息、社群参与与休闲 |

每题的选项关系由题库定义为“高度兼容 / 可沟通 / 明显不兼容”。维度分数取该维度题目兼容度的平均值，再按权重合计。题目回答缺失的用户不进入每日推荐生成；这使问卷成为匹配池的补充资格，而不是用不完整资料猜测。

分数仅用于排序和等级映射：`高度契合`（80+）、`值得认识`（65–79）、`可进一步了解`（50–64）。低于 50 不推荐。若两位候选分数相同，优先更久未被推荐、再按账户创建时间稳定排序，避免列表抖动。

### 可解释性

理由来自该候选对中得分最高、且双方已答的不同维度；同一维度最多生成一条。提醒来自最低但仍可沟通的维度；没有可沟通差异时显示中性的“建议在认识中继续交流生活节奏与期待”。理由只使用预先审核的模板与选项标签，不泄露对方底线、完整答案或牧者资料。

## API 与前台

新增 API：

- `GET /match/questionnaire`：当前题库、本人答案和底线标记。
- `PUT /match/questionnaire`：校验并保存完整问卷，最多 5 项底线。
- `GET /match/recommendations/today`：获取或生成当天推荐快照及匹配解释。

扩展现有资料 API 以维护性别和基础偏好；现有 `POST /match/:targetId/intent` 继续处理心动与跳过，并在操作成功后更新当天推荐项状态。

前端将现有“匿名匹配”页拆为：

1. 未完成问卷：展示进度、进入问卷。
2. 已完成问卷：展示当天最多 3 张候选卡。
3. 候选卡：匿名头像、年龄段、城市、信仰背景、匹配等级、理由、提醒、心动/跳过。
4. 双向心动：沿用现有私聊入口；不在推荐页额外开放完整资料。

## 错误处理与安全

- 生成批次使用事务与唯一约束，避免同一用户并发请求生成重复推荐。
- 不对未入池、问卷不完整或性别/偏好缺失的用户生成推荐，返回明确的待办项。
- 后端重新校验目标用户仍在匹配池，防止前端缓存候选绕过资格限制。
- 匹配理由不得包含联系方式、背书内容、精确出生年份、完整教会名称、完整答案或不可妥协项等敏感信息。
- 管理员可在现有审核体系中封禁用户；被封禁用户不会出现在新批次中。

## 测试与验收

新增单元测试覆盖：

- 异性、年龄、城市和关系状态过滤。
- 双向不可妥协项排除。
- 六维加权分数、等级映射、稳定排序和理由/提醒生成。
- 每日批次幂等、次日重新生成、当天问卷修改不重算。
- 问卷完整性和 5 项底线限制。

新增路由测试覆盖：

- 未满足旧入池资格或未完成问卷时不能得到推荐。
- 合格用户当天至多得到 3 名候选，且重复请求返回相同结果。
- 心动、跳过、双向心动仍保持现有权限和聊天行为。

发布前运行现有 `npm run verify:release --prefix server`，并将每日推荐流程纳入 `verify:mvp` 或独立的回归脚本。
